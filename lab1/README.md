## Часть 2

### Запуск сервиса api в собственном namespace. 
*sudo unshare --pid --mount --net --uts --ipc --user --map-root-user --fork --mount-proc ./api*
- Флаг pid задаёт процессу PID=1, т.е. думает сервис api думает, что стал root'ом.
- Флаг mount изолирует файловую системы
- Флаг net создаёт lo
- Флаг uts даёт возможность задать hostname в контейнере
- Флаг ipc выносит в своё пространство медпроцессное взаимодействие для контейнера
- Флаг user задаёт изолированное пространство имён пользователей и групп.
- Флаг map-root-user сделает так, что внутри контейнера процесс, выполняемый от имени root, в реальной машине будет выполняться от имени пользователя
- Флаг fork создаёт дочерний процесс, внутри которого и будет выполняться сервис api
- Флаг mount-proc нужен, чтобы внутри изолированной среды утилиты мониторинга не видели процессов за пределами контейнера

Запуск команды представлен на рисунке снизу:

Для успешного запуска от не root пользователя пришлось снять защиту от несанкционированного создания пользовательских пространств имён:

*sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0*

В результате выполнения команды получаем процесс, находящийся в собственном namespace. Внутри этого namespace процесс сервиса api работает от имени root, также имеет собственную сеть, hostname (если задать отличный от оригинального) и область видимости средств мониторинга (ps aux, запущенный внутри namespace не показывает процессы хоста):

## Часть 3

### CPU Throttling

Мы начали с создания новой контрольной группы для нашего API. Для этого мы выполнили команду sudo mkdir /sys/fs/cgroup/lab-api-cpu. Затем мы установили ограничение на использование процессорного времени: записали строку "50000 100000" в файл cpu.max. Это означает, что на каждый период в 100000 микросекунд (100 мс) нашему процессу разрешено использовать только 50000 микросекунд (50 мс), то есть ровно половину одного ядра. После этого мы проверили, что лимит применился, выполнив cat, и убедились, что значения корректны. Далее мы поместили наш процесс с PID 4925 внутрь этой cgroup, записав его идентификатор в файл

<img width="974" height="153" alt="image" src="https://github.com/user-attachments/assets/11659e45-55fd-4890-8f8a-1c66fcb3c59c" />

Перед тем как запустить нагрузку, мы решили посмотреть на исходную статистику процессора в нашей cgroup. Мы выполнили cat /sys/fs/cgroup/lab-api-cpu/cpu.stat. В выводе мы заметили, что счётчик nr_periods равен 4, а счётчики nr_throttled и throttled_usec пока находятся на нуле. Это ожидаемо, так как процесс ещё не начал активно потреблять CPU, и троттлинга (принудительной остановки) не происходило

<img width="798" height="238" alt="image" src="https://github.com/user-attachments/assets/053f3b0a-f9c5-415c-a810-5f76ecf789c5" />

Чтобы проверить наш лимит в действии, мы обратились к нашему API через браузер по адресу http://192.168.133.129:8080/burn. Мы дернули ручку /burn, которая, как мы знаем, запускает бесконечный цикл, нагружающий одно ядро процессора. На экране мы увидели ответ burning, что подтвердило успешный старт нагрузки.

<img width="492" height="132" alt="image" src="https://github.com/user-attachments/assets/702fd4c7-6b27-4b82-911c-1a20cb51e8c1" />

Спустя некоторое время мы снова заглянули в файл статистики cpu.stat, чтобы оценить, как отработал наш лимит. Мы сразу заметили кардинальные изменения: количество периодов (nr_periods) выросло до 379, а счётчик nr_throttled подскочил до 375. Это означает, что в 375 из 379 периодов наш процесс упирался в установленный лимит и был вынужден останавливаться. Показатель throttled_usec также значительно вырос и составил 20541837 микросекунд (около 20.5 секунд). Мы убедились, что механизм cgroups работает корректно: искусственное ограничение в 50% ядра успешно сдерживает наш процесс, вызывая ожидаемый троттлинг.

### Форк-бомба

Сначала проверяем текущее состояние cgroup lab-api-pids: значение pids.current показывает количество активных процессов, а pids.events позволяет увидеть случаи, когда система не смогла создать новый процесс из-за ограничения. Затем проверяем значение pids.max, которое установлено в 10. После этого запускаем stress-ng с параметрами --fork 50 --timeout 10s. Таким образом, программа пытается создавать большое количество дочерних процессов, а cgroup должна не позволить превысить установленный предел.
<img width="974" height="365" alt="image" src="https://github.com/user-attachments/assets/dd735c91-b693-444f-a214-a2b3cc05d893" />
Во время выполнения нагрузки значение pids.current достигает 10, то есть установленного максимума. При этом счётчик max в pids.events увеличивается и показывает большое количество попыток создать дополнительные процессы после достижения лимита. Это наглядно показывает работу механизма cgroups: несмотря на то, что stress-ng пытается создать до 50 процессов, количество одновременно существующих tasks в данной cgroup не превышает заданное значение 10.

## Часть 4
### Ограничение с помощью привилегий
Для начала с помощью следующей команды запретим внутри нашего контейнера дополнительные возможности с помощью ограничения привилегий:

*unshare --pid --mount --net --uts --ipc --user --map-root-user --fork \
  --mount-proc \
  setpriv --inh-caps=-all --ambient-caps=-all --bounding-set=-all \
    ./api*

<img width="958" height="136" alt="image" src="https://github.com/user-attachments/assets/739f5a67-064a-40d1-9c6c-1a0c467de01b" />

Эта команда помимо оговорённого в части 2 запускает процесс с указанными привилегиями, в данном случае с указанием отсутствия привилегий (у всех атрибутов стоит выключение). setpriv не запускает отдельный процесс, а подменяет свой процессом api (execve).
- Атрибут inh-caps влияет на передачу набора привилегий процессам-потомкам при exeve
- Атрибут ambient-caps делает так, что никакой набор привилегий не сохранится при exeve
- Атрибут bounding-set в данном случае навсегда лишает процесс шанса на получение какой-то привелегии даже от root'а

На картинке снизу демонстрируется, что пользователь внутри процесса не может изменить время, потому что не имеет на это прав.

### Блокировка системного вызова
С помощью команды ниже мы помимо вышеописанного запрещаем изнутри контейнера делать системный вызов, отвечающий за создание директории:
*systemd-run --user --wait --pty   -p SystemCallFilter="~mkdir"   -p SystemCallErrorNumber=EPERM   unshare --pid --mount --net --uts --ipc --user --map-root-user --fork   --mount-proc   setpriv --inh-caps=-all --ambient-caps=-all --bounding-set=-all /home/alexandr/Desktop/containerization-labs/lab1/api*

<img width="958" height="141" alt="image" src="https://github.com/user-attachments/assets/928cfdd3-6804-4988-b2fe-f953295d7fb0" />

- Флаг user запускает модуль от имени пользовательского менеджера systemd (user@UID.service), а не системного. Не нужен root. Настройки применяются в рамках сессии.
- Флаг wait задаёт ожидание выполнения команды
- Флаг pty подключает псевдотерминал (PTY) — чтобы вывод команды шёл в ваш терминал в реальном времени, как при обычном запуске.
- Seccomp фильтр SystemCallFilter="~mkdir" запрещает вызов mkdir
- SystemCallErrorNumber=EPERM указывает, что при вызове запрещённого вызова нужно вернуть ошибку Operation not permitted
