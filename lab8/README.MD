## Часть 1. Идея и контекст

Компания: Стартап «CloudNotes» (B2B SaaS для создания заметок).
Проблема: Все ошибки бэкенда сыпятся в один общий технический Telegram-чат. Разработчики (команда из 3 человек) устали от информационного шума (alert fatigue)
и пропускают действительно важные сообщения (например, падение базы данных) среди мусорных ошибок валидации.

Решение: Автоматический ассистент, который перехватывает ошибки, с помощью AI классифицирует их на «Critical» и «Warning», и сам раскладывает по нужным местам: критичные создают тикет, а некритичные просто пишутся в лог.

Как это работает:

Триггер: Приложение отправляет POST-запрос (Webhook) с текстом ошибки.

AI-шаг: Агент анализирует текст (по ключевым словам и смыслу) и выносит вердикт.

Действие (MCP): Если ошибка критичная — агент вызывает инструмент создания тикета (через MCP-сервер). Если нет — вызывает инструмент записи в лог (через второй MCP-сервер).

$$ Часть 2. Архитектура и компоненты

В workflow реализованы следующие обязательные элементы:

- Триггер: Узел Webhook в n8n.

- AI-шаг: Узел AI Agent с моделью из OpenRouter.

- MCP-серверы (2 шт.): Локальные серверы, которые дают агенту доступ к файловой системе.

- AI Toolkit: Агенту доступен инструмент write_file (запись файла).

- Skills: В системном промпте (System Message) агенту заданы правила: "Если видишь panic, database или timeout — это Critical, создай тикет. Если видишь invalid input или 401 — это Warning, сохрани в лог".

- Результат: Текстовый файл с отчетом на диске компьютера.

## Часть 3. Локальный запуск (и настройка VPN)

Для работы OpenRouter требовался VPN. Из-за этого возник конфликт: n8n (внутри Docker) не мог достучаться до MCP-серверов, так как VPN перехватывал локальный трафик.
Проблема была решена запуском n8n в сети хоста и правильной настройкой прокси.

Запуск MCP-серверов (2 шт.):

Сервер для логов (Warning) запускался так:
```docker run -d --name mcp-filesystem --network host -v "$(pwd)/mcp_data:/data" supercorp/supergateway --stdio "npx -y @modelcontextprotocol/server-filesystem /data" --port 8812```

Сервер для логов (Warning) запускался так:
```docker run -d --name mcp-tickets --network host -v "$(pwd)/mcp_tickets:/data" supercorp/supergateway --stdio "npx -y @modelcontextprotocol/server-filesystem /data" --port 8813```

Запуск n8n с учетом VPN:
Прокси (Xray) работает на порту 10809. Мы используем сеть хоста и прописываем исключения для локальных адресов, чтобы n8n видел MCP-серверы.
```
docker run -d \
  --name n8n \
  --network host \
  -v n8n_data:/home/node/.n8n \
  -e N8N_SECURE_COOKIE=false \
  -e N8N_METRICS=true \
  -e HTTP_PROXY=http://127.0.0.1:10809 \
  -e HTTPS_PROXY=http://127.0.0.1:10809 \
  -e NO_PROXY="localhost,127.0.0.1,::1" \
  n8nio/n8n
```
Тестирование (после активации кнопки "Published" в n8n):
Отправка критической ошибки (создаст файл в mcp_tickets):
```
curl -X POST http://127.0.0.1:5678/webhook/error-triage \
  -H "Content-Type: application/json" \
  -d '{"error": "panic: database connection timeout"}'
```
## Часть 4. Мониторинг

Мониторинг n8n настроен через встроенный экспортер Prometheus (флаг N8N_METRICS=true) и отображается в Grafana.

Собран дашборд n8n Monitoring с тремя основными панелями:

- n8n_active_workflow_count (Количество активных воркфлоу). Зачем: Если график падает до нуля, значит n8n перезагрузился, упал или воркфлоу случайно выключили. Бизнес-процесс встал. Алерт: == 0.

- n8n_nodejs_eventloop_lag_p99_seconds (Задержка Event Loop). Зачем: n8n работает на Node.js в один поток. Если AI-модель отвечает слишком долго или парсит огромные данные, Event Loop блокируется, и сервер перестает принимать запросы. Алерт: > 0.5 (500 мс).

- n8n_nodejs_heap_size_used_bytes (Использование памяти). Зачем: AI-агенты держат в памяти контекст диалогов. Если график памяти постоянно растет и не сбрасывается (сборщик мусора не справляется), контейнер упадет по OOM (Out of Memory). Алерт: > 500000000 (500 МБ).
